# log-load-generator
Load Generator for Logs written in Go

## Build
```
go build -o build/load-gen ./src/
```

Cross-compile for Linux:
```
GOOS=linux GOARCH=amd64 go build -o build/load-gen ./src/main.go
```

## AWS WAF Log Mode
Generate realistic AWS WAF v2 logs and send them to a ctrlb stream:
```
./build/load-gen \
  -logFormat=waf \
  -logFile=templates/waf_logs.json \
  -weightConfig=templates/waf_log_weights.json \
  -baseURL=http://staging.ctrlb.dev:8080 \
  -orgId=api/default \
  -streamName=waf_stream \
  -concurrency=2 \
  -batchSize=50 \
  -logsPerMinute=1000
```

## Text Log Mode (default)
Send flat text-based log lines (k8s, custom formats):
```
./build/load-gen \
  -baseURL=http://10.0.0.3:8445 \
  -logFile=templates/prod_log_k8_logs.json \
  -concurrency=20 \
  -batchSize=100
```

With weighted category selection:
```
./build/load-gen \
  -logFile=my_templates.json \
  -weightConfig=my_weights.json \
  -baseURL=http://staging.ctrlb.dev:8080 \
  -orgId=api/default \
  -streamName=ing_test \
  -concurrency=1 \
  -batchSize=10 \
  -logsPerMinute=1000
```

## Flags

| Flag | Default | Description |
|------|---------|-------------|
| `-logFormat` | `text` | `text` (flat log lines) or `waf` (AWS WAF JSON) |
| `-logFile` | `templates/prod_log_k8_logs.json` | Path to template JSON file |
| `-weightConfig` | (none) | Path to category weight config (required for `waf` mode) |
| `-weightSelection` | `quota` | `quota` (steady mix) or `random` (i.i.d. draws) |
| `-baseURL` | `http://10.0.0.3:8445` | Target ingest endpoint |
| `-orgId` | `ctrlb` | Organization ID |
| `-streamName` | `test_stream` | Stream/dataset name |
| `-concurrency` | `20` | Number of concurrent workers |
| `-batchSize` | `1000` | Logs per batch |
| `-logsPerMinute` | `0` | Rate limit (0 = unlimited) |
| `-targetVolumeGB` | `0` | Volume target in GB |
| `-useVolumeTarget` | `false` | Use volume-based instead of time-based termination |

## Fluent Bit -> S3 (dummy logs)

Run Fluent Bit in Docker to push dummy logs straight to S3 using the bundled config at [fluent-bit-conf/fb-dummy-s3.conf](fluent-bit-conf/fb-dummy-s3.conf). This emits dummy logs only (no load-gen involved) and is useful for verifying S3 write paths quickly. Objects are written as **gzip-compressed** files (`*.gz`).

```
sudo docker run --rm -it \
  -e AWS_ACCESS_KEY_ID="<>" \
  -e AWS_SECRET_ACCESS_KEY="<>" \
  -v $(pwd)/fluent-bit-conf/fb-dummy-s3.conf:/fluent-bit/etc/fluent-bit.conf:ro \
  -v fluent-bit-buffer:/tmp/fluent-bit \
  --name fluent-bit-test \
  fluent/fluent-bit:latest
```

Notes:
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` are only required when writing to **GCS** (via the S3-compatible API). On an EC2 instance with an attached IAM role, omit them — the AWS SDK picks up credentials from the instance metadata service automatically.
- Output is dummy data generated by Fluent Bit's `dummy` input; swap the config if you want to ship load-generator output instead.

## Fluent Bit HTTP -> S3 (load-gen as source)

Run Fluent Bit with an HTTP input and point the load generator at it. Fluent Bit buffers, gzips, and uploads to S3 automatically. Config: [fluent-bit-conf/fb-http-s3.conf](fluent-bit-conf/fb-http-s3.conf). Objects land in the bucket as **gzip-compressed** files (`*.gz`).

Start Fluent Bit (publishes the HTTP input on `:8888`):
```
sudo docker run --rm -it \
  -e AWS_ACCESS_KEY_ID="<>" \
  -e AWS_SECRET_ACCESS_KEY="<>" \
  -p 8888:8888 \
  -v $(pwd)/fluent-bit-conf/fb-http-s3.conf:/fluent-bit/etc/fluent-bit.conf:ro \
  -v fluent-bit-buffer:/tmp/fluent-bit \
  --name fluent-bit-http \
  fluent/fluent-bit:latest
```

Then run the load generator against it (any `orgId` / `streamName` works — Fluent Bit will accept the POST and tag it per the config):
```
./build/load-gen \
  -logFormat=waf \
  -logFile=templates/waf_logs.json \
  -weightConfig=templates/waf_log_weights.json \
  -baseURL=http://localhost:8888 \
  -orgId=api/default \
  -streamName=waf_stream \
  -concurrency=2 \
  -batchSize=50 \
  -logsPerMinute=1000
```

Same credential rules apply as above: `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` are only needed for GCS; on EC2 with an IAM role they can be omitted.
