# log-load-generator
Load Generator for Logs written in Go

## Build
```
go build -o build/load-gen ./src/
```

Cross-compile for Linux:
```
GOOS=linux GOARCH=amd64 go build -o build/load-gen ./src/main.go
```

## AWS WAF Log Mode
Generate realistic AWS WAF v2 logs and send them to a ctrlb stream:
```
./build/load-gen \
  -logFormat=waf \
  -logFile=templates/waf_logs.json \
  -weightConfig=templates/waf_log_weights.json \
  -baseURL=http://staging.ctrlb.dev:8080 \
  -orgId=api/default \
  -streamName=waf_stream \
  -concurrency=2 \
  -batchSize=50 \
  -logsPerMinute=1000
```

## K8 Log Mode
Generate K8 logs with the same fields as ClickHouse ingest (`_timestamp`, `ist_timestamp`, `message`, `trace_id`, `span_id`, `namespace_name`, `container_name`, `pod_name`, `plugin_source`, `stream`, `bytes`) and send to a ctrlb stream:
```
./build/load-gen \
  -logFormat=k8 \
  -logFile=templates/prod_log_k8_logs.json \
  -baseURL=http://staging.ctrlb.dev:8080 \
  -orgId=api/default \
  -streamName=k8_stream \
  -concurrency=10 \
  -batchSize=1000 \
  -logsPerMinute=60000
```

## Text Log Mode (default)
Send flat text-based log lines (`log` + `_timestamp` fields; use templates with a `log` field, e.g. `staging_logs.json`):
```
./build/load-gen \
  -baseURL=http://10.0.0.3:8445 \
  -logFile=templates/staging_logs.json \
  -concurrency=20 \
  -batchSize=100
```

With weighted category selection:
```
./build/load-gen \
  -logFile=my_templates.json \
  -weightConfig=my_weights.json \
  -baseURL=http://staging.ctrlb.dev:8080 \
  -orgId=api/default \
  -streamName=ing_test \
  -concurrency=1 \
  -batchSize=10 \
  -logsPerMinute=1000
```

## Flags

| Flag | Default | Description |
|------|---------|-------------|
| `-logFormat` | `text` | `text` (flat log lines), `k8` (K8/Fluent Bit JSON), or `waf` (AWS WAF JSON) |
| `-logFile` | `templates/prod_log_k8_logs.json` | Path to template JSON file |
| `-weightConfig` | (none) | Path to category weight config (required for `waf` mode) |
| `-weightSelection` | `quota` | `quota` (steady mix) or `random` (i.i.d. draws) |
| `-baseURL` | `http://10.0.0.3:8445` | Target ingest endpoint |
| `-orgId` | `ctrlb` | Organization ID |
| `-streamName` | `test_stream` | Stream/dataset name |
| `-concurrency` | `20` | Number of concurrent workers |
| `-batchSize` | `1000` | Logs per batch |
| `-logsPerMinute` | `0` | Rate limit (0 = unlimited) |
| `-targetVolumeGB` | `0` | Volume target in GB |
| `-useVolumeTarget` | `false` | Use volume-based instead of time-based termination |

## Fluent Bit -> S3 (dummy logs)

Run Fluent Bit in Docker to push dummy logs straight to S3 using the bundled config at [fluent-bit-conf/fb-dummy-s3.conf](fluent-bit-conf/fb-dummy-s3.conf). This emits dummy logs only (no load-gen involved) and is useful for verifying S3 write paths quickly. Objects are written as **gzip-compressed** files (`*.gz`).

```
sudo docker run --rm -it \
  -e AWS_ACCESS_KEY_ID="<>" \
  -e AWS_SECRET_ACCESS_KEY="<>" \
  -v $(pwd)/fluent-bit-conf/fb-dummy-s3.conf:/fluent-bit/etc/fluent-bit.conf:ro \
  -v fluent-bit-buffer:/tmp/fluent-bit \
  --name fluent-bit-test \
  fluent/fluent-bit:latest
```

Notes:
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` are only required when writing to **GCS** (via the S3-compatible API). On an EC2 instance with an attached IAM role, omit them — the AWS SDK picks up credentials from the instance metadata service automatically.
- Output is dummy data generated by Fluent Bit's `dummy` input; swap the config if you want to ship load-generator output instead.

## Fluent Bit HTTP -> S3 (load-gen as source)

Run Fluent Bit with an HTTP input and point the load generator at it. Fluent Bit buffers, gzips, and uploads to S3 automatically. Config: [fluent-bit-conf/fb-http-s3.conf](fluent-bit-conf/fb-http-s3.conf). Objects land in the bucket as **gzip-compressed** files (`*.gz`).

Start Fluent Bit (publishes the HTTP input on `:8888`):
```
sudo docker run --rm -it \
  -e AWS_ACCESS_KEY_ID="<>" \
  -e AWS_SECRET_ACCESS_KEY="<>" \
  -p 8888:8888 \
  -v $(pwd)/fluent-bit-conf/fb-http-s3.conf:/fluent-bit/etc/fluent-bit.conf:ro \
  -v fluent-bit-buffer:/tmp/fluent-bit \
  --name fluent-bit-http \
  fluent/fluent-bit:latest
```

Then run the load generator against it (any `orgId` / `streamName` works — Fluent Bit will accept the POST and tag it per the config):
```
./build/load-gen \
  -logFormat=waf \
  -logFile=templates/waf_logs.json \
  -weightConfig=templates/waf_log_weights.json \
  -baseURL=http://localhost:8888 \
  -orgId=api/default \
  -streamName=waf_stream \
  -concurrency=2 \
  -batchSize=50 \
  -logsPerMinute=1000
```

Same credential rules apply as above: `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` are only needed for GCS; on EC2 with an IAM role they can be omitted.

## Vector HTTP -> Object Storage (load-gen as source)

Vector is an alternative ingest agent. Unlike the Fluent Bit setup it uses **native** GCS / S3 SDKs (not the S3 XML-compat API), which avoids the connection-reset issues seen with `out_s3` against `storage.googleapis.com` under load. Both configs expose the same HTTP input on `:8089` so the load-gen command is unchanged.

### Vector -> GCS
Config: [vector-conf/vector-gcp.toml](vector-conf/vector-gcp.toml). Uses Vector's `gcp_cloud_storage` sink. On a GCE host, credentials are picked up automatically from the VM's default service account via the metadata server — no env vars required.

```
sudo docker run --rm -it \
  -p 8089:8089 \
  -p 8686:8686 \
  -v $(pwd)/vector-conf/vector-gcp.toml:/etc/vector/vector.toml:ro \
  --name vector-gcp \
  timberio/vector:latest-debian \
  --config /etc/vector/vector.toml
```

If running off-GCP, mount a service-account JSON and add `credentials_path = "/etc/vector/sa.json"` (or `api_key = "..."`) under `[sinks.gcs_out.auth]`.

### Vector -> S3
Config: [vector-conf/vector-aws.toml](vector-conf/vector-aws.toml). Uses Vector's `aws_s3` sink. Credentials follow the standard AWS chain — env vars, shared credentials file, or instance/role profile.

```
sudo docker run --rm -it \
  -e AWS_ACCESS_KEY_ID="<>" \
  -e AWS_SECRET_ACCESS_KEY="<>" \
  -p 8089:8089 \
  -p 8686:8686 \
  -v $(pwd)/vector-conf/vector-aws.toml:/etc/vector/vector.toml:ro \
  --name vector-aws \
  timberio/vector:latest-debian \
  --config /etc/vector/vector.toml
```

On EC2 with an IAM role, omit the `-e AWS_*` flags. Update `bucket` and `region` in the config to match your S3 bucket.

### Load generator (either sink)
```
./build/load-gen \
  -logFormat=waf \
  -logFile=templates/waf_logs.json \
  -weightConfig=templates/waf_log_weights.json \
  -baseURL=http://localhost:8089 \
  -orgId=api/default \
  -streamName=waf_stream \
  -concurrency=6 \
  -batchSize=1000 \
  -logsPerMinute=100000
```

### Observability
Vector exposes a Prometheus-style metrics endpoint on `:8686/metrics`:
```
curl -s http://localhost:8686/metrics | grep -E 'vector_component_(sent|received)_events_total|vector_component_errors_total'
```
If `sent_events_total` for the sink keeps climbing and `errors_total` stays flat, no data is being lost.
